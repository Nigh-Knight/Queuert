<decisions_made>

## Authentication Architecture
- **Decision**: No phone OTP, QR-based volunteer access, admin verification code
- **Rationale**: Events are time-sensitive, phone+name sufficient for service users, QR prevents unauthorized volunteer access
- **Impact**: Simpler auth flow, faster onboarding, admin controls who joins

## Backend-First Development
- **Decision**: Build functional backend + placeholder UI first, Builder.io integration separate
- **Rationale**: Backend logic is testable independently, UI being redesigned at 7pm today
- **Impact**: Phases 1-10 deliver working features with basic UI, Builder.io swaps visuals later

## Google Sheets Strategy
- **Decision**: Batch export every 60 seconds, not real-time per action
- **Rationale**: Avoid rate limits (300 req/min), research confirmed batching prevents issues at scale
- **Impact**: Slight delay in Sheets updates, but prevents quota exhaustion

## Offline Capability
- **Decision**: Read-only queue view when offline, network required for modifications
- **Rationale**: Simpler implementation, avoids conflict resolution complexity
- **Impact**: Volunteers can view queue offline but need connection to manage it

<context>

## Project Vision

Queuert replaces paper-based queue management for Laundry Love events serving people experiencing homelessness. Core value: volunteers efficiently manage queue + timers in real-time, service users know their position and when wash completes.

## Technical Stack (Validated)

- **Frontend**: Expo 54, React 19.1, React Native 0.81
- **Backend**: Convex 1.31.6 (real-time operational DB)
- **State**: React useState (local), Zustand installed but not yet integrated
- **UI**: Existing atomic components + screens (will be replaced with Builder.io)
- **Routing**: Expo Router (file-based)
- **Theme**: Centralized constants in constants/theme.ts

## Architecture Patterns (From Research)

- **Convex reactive queries**: useQuery creates WebSocket subscriptions, auto-updates on mutations
- **Server-side timers**: Store timerStartedAt + duration in DB, scheduled function checks expiration every 10s
- **Optimistic UI with rollback**: Mutations feel instant but must implement error handling
- **Index-first querying**: All filters use .withIndex() for performance

## Development Flow

1. Each phase: Plan → Execute → Verify (if enabled)
2. Backend functions first (mutations, queries, scheduled functions)
3. Wire to placeholder UI screens using existing atoms
4. Test real-time sync across devices
5. Builder.io replaces UI later (outside GSD workflow)

## Key Research Insights

- **Timer drift is critical**: Must use server-authoritative approach from day 1, can't retrofit
- **Offline complexity**: Read-only cache sufficient for MVP, validate connectivity issues before investing in CRDT sync
- **Google Sheets batching**: 60s intervals prevent rate limits, exponential backoff on failures
- **Spanish is table stakes**: Multi-language support essential for LA/SF events

</context>
